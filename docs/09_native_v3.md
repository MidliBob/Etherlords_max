# Native v3 — починка динамики: create-scale, маркер, design-константы экранов

Статус: **собиратель готов и верифицирован** (`tools/patch_native_v3.py`, тесты T1–T7,
52 проверки зелёные), ожидает полевой приемки на Windows (§5). База — v2 (docs/08);
все хуки v2 сохранены (P1, H1, H2', H3).

Повод: полевая приемка v2 (1600x900): главное меню идеально; **меню сохранения/
загрузки** — часть интерфейса съехала (тексты строк списка левее таблицы, превью сохранений и рамки вне своих панелей); **глобальная карта** — часть интерфейса
съехала и кнопки колеса не работают: hover зажигается, когда курсор **правее**
нарисованной кнопки.

---

## 1. Почему v2 ломал именно эти экраны (три механизма)

### 1.1 Контролы, созданные после `CScreenManager::Init`
Пост-проход v2 (H2) обходит список менеджера `[0x82b968]` **один раз** внутри
`apply_layout`. Всё, что создаётся позже, остаётся в design-координатах, пока
цепочка родителей уже масштабирована. Отсюда два разных симптома:

* **hover правее нарисованного** (колесо, часть кнопок adv-экрана): draw идёт по
  абсолютным design-rect'ам визуала/спрайтов, а hit-test суммирует
  parent-relative rect'ы (`+0x154`/`+0x174` + цепочка родителей, 0x58fb70) —
  масштабированной цепочки; разница = (k−1)·Σorigin родителей → зона hover
  уезжает вправо-вниз от нарисованного;
* **съехавшие элементы диалогов**: код экранов создаёт контролы лениво
  («FindControl-or-create»: 0x502347/0x5028d3 и др., `new` + ctor при входе на
  экран/открытии диалога), а также клонирует/пересоздаёт их при обновлении.

Точка регистрации контрола в менеджере **единственная**: `0x58bbc0`
(`AddControl`: вызывается из хвоста ctor'а 0x58f2f2; других вызовов нет).

### 1.2 CButtonList: собственный массив спрайтов
Колесо команд/списки кнопок — `CButtonList` (vtable `0x75d498`): hover
(`PtInRect` в Draw 0x57cfc3–0x57d000) и отрисовка спрайтов идут по rect'ам
**собственного массива** `[elem+0x1c0]` (count `[elem+0x1c4]`, шаг 0x34,
rect спрайта `+0x14`), который v2 не масштабировал никак, тогда как rect'ы
самого контрола (`+0x154/0x164/0x174`) и визуал — масштабировал. Любая
несостыковка этих двух пространств = hover мимо нарисованного спрайта.

### 1.3 Design-константы в коде экранов
Экранные классы хранят layout-константы в глобалах и immediate и смешивают их с
масштабированными полями:

* `CSaveScreen` (меню сохранения/загрузки): блок глобалов `0x829540..0x82964c`
  (setter 0x53db8c..0x53de78, все значения — immediate): rect'ы панелей/колонок/
  областей списка, пара xy `0x829550/54` (добавляется к **масштабированному**
  `active` в Draw 0x53f8b1–0x53f8d7 → смешанный сдвиг превью/маркера);
  row-layout 0x53ec30 строит rect'ы строк из колонок `0x829610..0x82964c` →
  тексты строк при native оставались в design (наблюдение на скриншоте:
  имена/даты левее масштабированной сетки, питч 26 вместо 26·k);
* `CSelectMission::Draw` 0x5461bc: хардкод-рамка диалога (158,111,866,661)
  + 10 вложенных OffsetRect(1,1) при flag==1 — при native рисовалась поверх
  масштабированного диалога в design-позиции.

Пиксельные размеры (например `0x8295a8/ac` = 256x192 превью сохранений)
**не** масштабируются — это размеры source-текстуры.

## 2. Карта правок v3 (добавки к v2; file = VA − 0x400000)

| # | сайт VA (file) | байты | замена |
|---|---|---|---|
| H4 | 0x58BBC0 (0x18bbc0) `AddControl` | `568b742408` | jmp `add_stub` |
| H5a | 0x53F830 (0x13f830) `CSaveScreen::Draw` | `56578bf1e8` | jmp `draw_stub` |
| H5b | 0x53EC30 (0x13ec30) row-layout | `6aff685180` | jmp `rowl_stub` |
| H6 | 0x5461BC (0x1461bc) рамка CSelectMission | `c74424149e` | jmp `sel_stub` |

Code cave тот же (file 0x355656..0x356000); занято 2254/2474 байта:
`trampA, post_scale', scale_rect, scale_one, maskfix, add_stub, savefix,
savefix_tbl(744 Б данных), draw_stub, rowl_stub, sel_stub`.

### 2.1 Маркер-протокол (idempotence + защита от двойного масштаба)
`[elem+0x14c]`, nibble: `(nibble & 0xC) == 0x4` ⇒ «масштабирован mod'ом».
ctor пишет nibble=0xF (0x58f2cf), apply_flag — 1/2, ванильных 4..7 не бывает
(флаги 2/3 не возникают, docs/08 §5.6); бит 0x8 не используем (входит в 0xF
ctor'а). Пост-проход и H4 ставят маркер; повторные проходы пропускают
помеченных (побочный фикс риска v2 «повторный apply_layout» для списка).

### 2.2 scale_one(eax=elem, edx=force)
Общая процедура пост-прохода и H4: маркер → (force==0: гейт «голова списка
помечена», т.е. пост-проход уже был) → живой режим `[0x825de8]`, base по
`[0x82722c]+0x188` → k==1: только маркер → масштаб: `+0x154/+0x164/+0x174`,
active `+0x1ac/+0x1b0`, визуал (`+0x40/+0x18` subnode'ов), **спрайт-rect'ы
CButtonList** (`[+0x1c0]`, i·0x34+0x14, i<count; `+0x28`-texture не трогается)
→ маркер. Records `+0x18c/+0x19c` и sX/sY не трогаются (идемпотентность
relayout), маски `+0x150` не трогаются (H3).

### 2.3 H4 add_stub (scale-on-create)
Пролог `AddControl` (push esi; mov esi,[esp+8]): pushad → scale_one([esp+0x24],
force=0) → popad → украденные 5 байт → jmp 0x58BBC5. Гейт головы списка
отключает H4 до пост-прохода (контролы Init масштабируются пост-проходом, а не
дважды).

**Крах первой сборки v3 и его фикс (post_done).** Первый вариант гейта читал
`[[[0x82b968]]+0x1c]+0x14c` напрямую — на ПЕРВОМ же контроле загрузки
Controls.reg список менеджера ещё пуст (sentinel: `[head+8]==head`,
`[head+0x1c]==0`), и розыменование `[0+0x14c]` давало access violation при
запуске. Гейт вынесен в общую процедуру `post_done` (eax=1/0) с проверками на
каждом шаге: mgr!=0, head!=0, node!=[head] (пусто), node+0x1c!=0, и только затем
маркер; плюс null-check `[0x82722c]` во всех трёх гейтах. Покрыто тестом T5c
(пустой список и mgr=null — проход без краха, контрол не тронут). Ре-parent (`0x58f6c0`/`0x57c900`) после H4 работает по согласованным
масштабированным rect'ам.

### 2.4 H5 fix_save_consts (идемпотентно, из запечённых design-значений)
`savefix` + таблица `savefix_tbl` (62 тройки (addr, design, axis); значения
сняты с immediate setter'а 0x53db8c..0x53de78): `[addr] = design·W/1024` (axis X:
field0/2) или `design·H/768` (axis Y: field1/3) — правило осей верно и для
LTRB, и для xywh. Гейт: flag==1, голова помечена, (W,H)≠(1024,768). Вызывается
из прологов `CSaveScreen::Draw` (H5a, перед украденным call 0x5905d0) и
row-layout 0x53ec30 (H5b) ⇒ и отрисовка, и построение строк видят native-
константы; повторные вызовы перезаписывают из констант (не накопительно).
`0x8295a8/ac` (пиксельный размер превью) исключены.

### 2.5 H6 sel_stub
0x5461bc: gate=true → пишем (158,111,866,661)·k в слоты `[esp+0x14..0x23]`,
jmp 0x5461DC (оригинальные mov edi/ebp/ebx = source-rect текстуры 225,45,235,55
не масштабируются); gate=false → design mov#1 + jmp 0x5461C4 (mov 2..4).

## 3. Что стало с потребителями (docs/04)

* **draw**: визуал/спрайты/тексты строк — native (scale_one при создании +
  savefix-константы для row-layout);
* **hover/click**: те же масштабированные rect'ы/маски + спрайт-rect'ы
  CButtonList (теперь в одном пространстве с draw); maskfix (H3) без изменений;
* **live-поверхности**: без изменений (native от рождения).

## 4. Верификация сборщика (встроена, всегда)
1. Контрольные байты 10 сайтов (P1a–c, H1–H4, H5a/b, H6).
2. Capstone-аудит cave: 375 инструкций, цели ветвлений только в разрешённом
   наборе (возвраты сайтов, VA_ITER, VA_DRAWBASE, части cave); байт без остатка.
3. Аудит диффа: изменены только сайты + cave.
4. Интерпретатор i386: T1 trampA; T2 maskfix; T3 post_scale'+маркеры;
   T4 identity+идемпотентность; T5 add_stub (scale-on-create + гейт головы);
   T5c add_stub при пустом списке/mgr=null (null/empty-safe гейт, регресс краха
   старта); T6 savefix (пересчёт констант, px-размер не тронут, регистры/esp
   целы); T6b спрайт-rect'ы CButtonList; T7 sel_stub (gate on/off).
   55 проверок OK; cave 2342/2474, capstone 391 инструкция.

## 6. Остаточные риски / следующая итерация
1. **Блок 0x827d80..0x828000 (adv-экран)**: часть глобалов пишется рантаймом
   (0x506dxx) из производных величин; если приемка покажет съехавшие панели
   adv-экрана при консистентном hover — лечить хуком-пересчётом этого блока по
   образцу savefix (нужна трассировка рантайм-writer'ов).
2. Row-layout: базы Y строк берутся из членов экрана, вычисляемых из rect'ов
   контролов; если тексты строк всё ещё дрейфуют по Y — добавить эти члены в
   таблицу savefix (значения читаются из 0x53ec30..0x53f200).
3. Маркер живёт в nibble `+0x14c`: если будущий патч 1.08 изменит семантику
   nibble — перепроверить (grep `and …,0xf` по +0x14c в docs/09 §2.1).
4. Клон-контролы, создаваемые и настраиваемые до первой отрисовки экрана,
   масштабируются H4 в момент регистрации; если какой-то экран переставляет их
   design-delta после регистрации (0x503580 OnLayoutChange-путь) — позиция
   будет design+k·init: лечится включением соответствующих immediate в таблицу
   savefix-образного хука этого экрана.

# Дополнение v3.1 (сборка v4): итоги полевого прогона v3 и новые хуки

## 0. Что показал прогон v3 (1600x900)
* запуск ОК (фикс краха пустого списка, §2.3);
* меню загрузки: шапка таблицы (ДАТА/ВРЕМЯ) встала в масштабированные колонки,
  blazon (герб) встал в низ инфо-панели (пара 0x829550/54 работает);
  **но**: превью сохранений исчезло, тексты строк остались в design;
* глобальная карта: колесо по-прежнему мертво (hover мимо нарисованного).

## 1. Регресс превью и ревизия таблицы savefix
Тюплы `0x829558..94`, `0x829598..a4`, `0x8295b0..bc` используются blit'ом превью
(0x53f4e0..0x53fb9c) как **source-rect'ы/clip-регионы текстуры** в пиксельном
пространстве: их масштабирование сужало копию до полоски → превью «исчезло».
Таблица `savefix_tbl` урезана до доказанных полей: пара `0x829550/54` (якорь
спрайта от active) и rect'ы колонок `0x829610..64c` (шапка/колонки). Превью
вернулось к состоянию v2 (рисуется, позиция неточна) — см. §3 остаточные.

## 2. H7: scale-aware set_rect (0x58f690) — класс «рантайм-перестановок»
Код экранов (adv: 0x503580/0x50bf00/0x5036ca и др.) переставляет контролы
**после** Init вызовами `set_rect` с design-rect'ами (parent-relative), при этом
`set_rect` пишет только `+0x154` и не трогает визуал: hit-цепочка получает
design-звено в масштабированной цепи, а draw остаётся в scaled-визуале →
hover/click уезжают от нарисованного (колесо команд, adv-панели). Это и есть
стойкий симптом колеса, который не лечился ни v2, ни v3.0.

H7: пролог `set_rect` (6 байт, `mov eax,[esp+4]; mov edx,[eax]`): если контрол
помечен маркером (пост-проход был) и k!=1 — входящий rect домножается на k
(копия в кадре стаба, указатель подменяется в стек-слоте аргумента; `ret 4`
чистит стек как обычно), иначе — байт-в-байт оригинал. Непомеченные контролы
(Init-загрузка Controls.reg) не затрагиваются. Тест T6c: marked→scaled,
unmarked→passthrough, k==1→passthrough, esp/ret-4 баланс.

## 3. Остаточные известные проблемы (следующая итерация)
1. **Тексты строк списка сохранений**: позиции строк кэшируются CTextArray
   (объект текста списка) в design-координатах на Init и не перекэшируются при
   open; колонки/шапка уже масштабируются (savefix). Лечение: найти layout-
   функцию CTextArray (xref 0x586401/0x57b880) и вызывать её после open либо
   масштабировать её кэш напрямую.
2. **Позиция превью сохранений**: blit 0x53f4e0 смешивает live W/H, px-размер
   (0x8295a8/ac) и rect'ы-источники; требуется runtime-трассировка (CE-протокол
   docs/06) либо хук dest-вычисления 0x53f8d7.
3. Если колесо на v4 всё ещё неточно: снять скрин глобальной карты с курсором в
   момент hover (видно, какая зона светится) — по смещению вычислим, какое звено
   цепи (panel 0x1e0 / slot 0x27c / сектора) осталось в design, и добавим его в
   H7-подобный хук точечно.

# Дополнение v4→v5: post-mortem v4 и откат H7; debug-логгер

## 1. Post-mortem v4 (полевые кадры)
* **Главное меню: тексты кнопок съехали вправо** — H7 (scale-aware set_rect)
  домножал на k rect'ы, которые вызывающий код уже вычислил в native
  (центровка текстов кнопок читает rect кнопки и пишет текстовый контрол
  set_rect'ом). Двойной масштаб. Вывод: предпосылка H7 («входы set_rect —
  design») неверна для значимой части вызовов; H7 удалён из release.
* **Колесо: hover ушёл ещё дальше вправо** — тот же двойной масштаб на
  native-входах перестановки колеса. Значит, рассогласование колеса v2/v3
  создаёт НЕ set_rect с design-входом, а другой механизм (visual не догоняет
  hit-rect при перестановке, либо draw читает design-якорь). Требуется
  runtime-трассировка.
* **Меню загрузки: тексты строк слиплись в полосу** — масштабирование колонок
  `0x829610..64c` сдвинуло шапку, но строки рисуются из кэша CTextArray
  (design) → рассинхрон шапки/строк внутри одного текста. Колонки исключены
  из savefix_tbl; в таблице осталась только пара 0x829550/54 (герб).

## 2. v5 (release)
= v3.1 без H7 и без колонок в savefix: главное меню как в v2/v3 (эталон),
меню загрузки = v3 + герб на месте + превью как в v2, колесо = симптом v3
(hover правее). Тесты 53/53, cave 1622/2474.

## 3. v5dbg (debug-логгер, `--debug`)
H8/H9: бинарный лог в `el_evt.log` (рабочий каталог игры) каждого вызова
`set_rect` и `OnLayoutChange` после пост-прохода: kind, this, vtable, return
address вызывающего, marker, rect/дельты. Рекорд 44 Б, лимит 20000, handle
кэшируется в свободных dword'ах .data 0x829764/0x829768 (xref'ов нет).
**Поправка 0.0.8:** dword'ы 0x829764/0x829768 НЕ свободны — их пишет сама игра
(`mov [0x829764],0xa1` @0x54191e, `mov [0x829768],edx` @0x541bfc,
`mov ebx,0x829768` @0x5428de — блок констант экрана сохранений); отгруженная
v5dbg их фактически не использовала (в её cave нет ссылок — проверено по байтам),
но повторно брать их нельзя. Состояние логгера 0.0.8 — проверенно свободные
0x830040/0x830044, см. доп. 0.0.8.
Разбор: `python3 tools/decode_evtlog.py el_evt.log [vtable]`.
Протокол: запуск v5dbg → главная заставка → загрузить сохранение → глобальная
карта → курсор по центру колеса и секторам, 2–3 клика → выход из игры → прислать
el_evt.log. По ret-адресам восстанавливаем сайт перестановки колеса и то, какое
поле (visual/+0x154/+0x164/+0x174) остаётся в design.

# Дополнение 0.0.8: логгер — в каждой сборке по умолчанию

## 1. Решение и мотивация
В репозитории больше нет исходного бинарника (0.0.6: `reference/Etherlords.exe`
и сборки исключены из отслеживания). Единственный канал runtime-данных для
итераций — полевые прогоны на Windows и их логи. Поэтому с 0.0.8 сборщик
по умолчанию собирает **v6dbg** (логгер H8/H9 в каждой сборке): каждый запуск
игры сам по себе приносит данные (set_rect/OnLayoutChange: kind, this, vtable,
ret-адрес вызывающего, marker, rect/дельты — 44 Б/рекорд, `el_evt.log` в cwd
игры). Чистый release — `--no-logger` (`--debug` оставлен как устаревший no-op).

Философия прежняя (полевая практика v5dbg: лог не мешает), но теперь корректная:
H10 (evt_hit) не включён — с ним cave переполняется (доп. 0.0.6).

## 2. Поведение лога (новое в evt_write)
* **Лог = последний сеанс**: первое событие процесса усекает старый `el_evt.log`
  (CREATE_ALWAYS, флаг-состояние 0→1), последующие — append (OPEN_ALWAYS).
  Протокол сдачи данных не меняется: поиграть → выйти → прислать `el_evt.log`.
* **Лимит**: после 20000 рекордов за сеанс записи прекращаются (~880 КБ
  максимум; защита от безлимитного роста в долгих партиях).
* Ошибка CreateFileA (нет прав на cwd) — тихий выход, как в v5dbg.
* Формат рекорда и `tools/decode_evtlog.py` без изменений (kind 1/2).

## 3. Состояние логгера: ПРОВЕРЕННО свободные dword'ы .data
Флаг сессии = **0x830040**, счётчик рекордов = **0x830044** (нулевой виртуальный
хвост `.data`: RVA ≥ 0x417000 не имеет файловых байт, загрузчик зануляет;
секция R+W — `.text` не записываем, хранить состояние в cave нельзя).

чистые).

## 2. Статика CButtonList::Draw (0x57cf60, capstone по билду 409d3e08…)
* курсор читается ОДИН раз на Draw из `[screen+0xe0]`/`[screen+0xe4]`

* формально оба потребителя геометрии берут +0x14 (масштабируется с v3),
  значит рассинхрон либо в пространстве КУРСОРА (`[screen+0xe0/e4]`: писатели

  origin визуала/родителя отдельно от rect'а массива. Статика здесь упирается
  в运行时-значения: нужны пары (cursor, rect) в момент hover.

маркер колеса — помечен ли контрол вообще).

## 4. evt2txt.py — текстовая версия лога для пересылки
Загрузчики чатов/почты браковали сырой лог («ошибка разбора документа»):
бинарное содержимое не проходит даже под именем .txt. `tools/evt2txt.py`
(только stdlib; положить в папку игры и запустить, двойной клик поддерживается)
преобразует `el_evt.log` в чисто текстовый `el_evt_decoded.txt` рядом с логом;
шапка: исходник, число рекордов по kind, разрешение сеанса (автосъём по
полосам apply_layout). Формат строк = decode_evtlog.py + строки hover kind=3.
