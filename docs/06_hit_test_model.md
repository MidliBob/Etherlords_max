# Модель hit-test (уточнено после вашего уточнения)

## Факты

| Конфиг | rect (экран для hit-test/миникарты) | baked-таблица якорей | Кнопки |
|---|---|---|---|
| Оригинал, 1024x768 | 1024x768 | 1024x768 (flag=1) | работают |
| Оригинал, 1600x900 | **native 1600x900** | 800x600 (дефолт, вызов раскладки пропущен) | **НЕ работают** |
| layout1024 (exp B), 1600x900 | 1024x768 | 1024x768 (flag=1 форсирован) | **работают** |
| native v1, 1600x900 | **native 1600x900** | 1024x768 | **НЕ работают** |

## Вывод (инвариант)

Hit-test привязан к **rect**; отрисовка якорного UI — к **baked-таблице**.
Кнопки живы **тогда и только тогда, когда rect == размер baked-раскладки**.

- Оригинал@1600: rect=native, таблица=800 → расхождение → мёртвые кнопки (это
  существовало ДО моих правок; v1 их не сломал, а лишь не починил).
- layout1024@1600: rect=1024 и таблица=1024 → согласовано → кнопки живы.
- native v1@1600: rect=native, таблица=1024 → расхождение → мёртвые кнопки.

## Следствия

1. **layout1024 — безопасный функциональный базис**: на 1600x900 кнопки работают,
   UI в раскладке 1024x768 (с полями). Можно пользоваться сейчас, пока делаем native.
2. **Native требует привести baked-координаты элементов к native**, чтобы rect=native и
   элементы=native совпали. Это ровно пост-масштабирование координат элементов после
   `call 0x99fcb0` (план deep RE, `hook_skeleton.py`). Менять только rect нельзя (v1).
3. Меню/фон (нативная текстура 1024x768) — отдельный путь; его согласование идёт после
   основного хука.

## Уточнение от пользователя (оригинал @1600x900): три потребителя координат

Наблюдение: интерфейс **нарисован** как для 800x600 (верх-лево), но при водении мышью
**по периметру** экрана кнопки **подсвечиваются** (hover), а **клики не срабатывают**.

Значит потребителей координат три, и они расходятся:

| Потребитель | Источник | Позиция @1600 (оригинал) |
|---|---|---|
| Отрисовка якорного UI | baked-поля раскладки (`[esi+0xec/0xf0/0xf4…]`) | 800x600 (верх-лево) |
| Hover / подсветка | экранный rect (native) | native → подсветка по периметру |
| Click / dispatch | требует совпадения hover-элемента (rect) и baked-раскладки | не срабатывает НИ по периметру, НИ по нарисованным кнопкам |

Дополнительный факт: клик по НАРИСОВАННЫМ кнопкам тоже не работает и не подсвечивает их.
Значит click ≠ baked и click ≠ rect по отдельности; он сходится только когда hover-элемент
(rect-native) и baked-раскладка согласованы. Отсюда инвариант неизменен: rect == baked.

Это согласуется со всеми прошлыми замерами:
- original@1600: rect=native, baked=800 → hover native, draw/click 800 → «подсветка есть, клика нет».
- layout1024@1600: rect=1024 и baked=1024 → все три совпадают → клики живут.
- native v1@1600: rect=native, baked=1024 → hover/minimap native, draw/click 1024 → клики мертвы.

## Следствие для v2 (важное)

Hover УЖЕ считает нативные позиции от rect. Значит целевые позиции элементов на native
— это ровно там, где сейчас возникает подсветка. После пост-масштабирования baked-полей
до native все три потребителя сойдутся: нарисованные кнопки встанут туда, где сегодня
«призрачно» подсвечиваются, и клики заработают там же. Это даёт бесплатный визуальный
ориентир для проверки v2: совпало нарисованное с зоной подсветки = согласовано.

Альтернативная формулировка фикса: привести baked-поля (`[esi+0xec/0xf0/0xf4…]`)
в равенство с rect (native), т.к. инвариант = rect == baked. Пост-масштабирование
координат элементов — более общий способ достичь того же и не зависеть от того,
какие именно поля читает draw/click.

## Корректировка протокола шага 1

Базис для CE-скана удобнее взять **layout1024 @ 1600x900**: там кнопки живы и правая
колонка X=870 (таблица 1024). Scan Exact=870 → переключить разрешение/ресайз так, чтобы
произошла перезапись раскладки → Find what writes. Получим инструкцию записи X элемента
и offset поля — то, что нужно для пост-масштабирования.
